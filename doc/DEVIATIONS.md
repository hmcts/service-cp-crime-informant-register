# Parity Deviations Register

Behaviour-parity is the rule (constitution Principle I): the observable behaviour of this
service is defined by the legacy informant register function app plus the golden fixtures.
Every deliberate divergence from legacy behaviour MUST be recorded here, with review sign-off,
before the code that introduces it merges. The golden-file harness fails on any divergence
not listed in this register.

| # | Deviation | Legacy behaviour | New behaviour | Rationale | Approved |
|---|---|---|---|---|---|
| 1 | Verified TLS on the payload fetch | Redis client connects with `rejectUnauthorized: false` (certificate checks disabled) | TLS certificate verification enabled, platform CA bundle | Security defect (D14 in the design defect register); not observable in register output | Design sign-off 19 Aug 2026 (Option 2 page: the only improvements in this delivery are transport-level) |
| 2 | Transport reliability | Final POST errors swallowed at three levels; no retry; hearing silently lost | Failures retry (broker redelivery), then dead-letter with alerting; POST client retries connect/IO/5xx/429 | The single agreed improvement of the lift-and-shift (Option 2 page, "Scope"); changes failure behaviour only, never successful-path output | Design sign-off 19 Aug 2026 |
| 3 | **Waiver — alert wiring deferred (CRA-220 only)** | No signal of any kind: no logs, no metrics, no alerts | CRA-220 ships the full failure signal — a sanitised ERROR log and a failure metric on every failure path, plus countable dead-lettered messages (spec FR-017) — but **no dashboards or alert rules**. Alert wiring lands with the later operability story (`doc/TECHNICAL_DESIGN.md`, "Later stories": DLQ alert wiring and reconciliation tooling) | Named waiver of constitution Principle VI's "alerting is required in addition" clause, scoped to this increment. The walking skeleton has no real submission adapter, so there is nothing yet whose failure an on-call alert would act on; the emitted metrics are the prerequisite the alert rules are built from, and shipping them first keeps the waiver time-boxed. Still a strict improvement on legacy silence. Dead-letter **depth** is observed in deployed environments from Azure Monitor's native Service Bus metric `DeadletteredMessages` rather than polled by service code, so the deferred DLQ alert will be wired onto that platform metric; the service's own `informantregister_deadlettered_total{reason=…}` counter ships now alongside it | Gate-2 spec review, 20 Aug 2026 — expires when the operability story lands; follow-up ticket to be raised on the CRA board |

| 4 | No fragments is an empty list, not `undefined` | `SetInformantRegisterBuilder.build()` returns `undefined` twice over — for a hearing with neither `prosecutionCases` nor `courtApplications`, and for one whose loop yields no fragments. `InformantRegisterOrchestrator`'s `if (informantRegisters)` then skips subscription matching, the outbound mapping and the POST, and the orchestration still reports success | `RegisterBuilder.build()` returns an empty list. The pipeline records the run COMPLETED with the reason `no-authorities` | Nothing is submitted on either side and no register content differs: the divergence is that the port's answer is a value the state machine can record rather than an absence every caller has to test for. `design_rules.md` ("Processing State Machine") requires exactly that — a hearing that legitimately produces no authorities ends COMPLETED with `no-authorities`, a business outcome and not an error. Pinned by `RegisterBuilderParityTest.assertLegacyProducedNothing`, which asserts the empty list on cases 08 and 09 and fails on a populated one — a port that found authorities the legacy did not is an unregistered divergence and must not reach a prosecuting authority. Note the boundary: this covers a hearing the legacy has *no register for*. A hearing the legacy *throws* on is a different case and is covered by entry 5 — those now surface as a non-transient failure and dead-letter, never as an empty result | **Sign-off pending** — raised by the Story-2 code review, 22 Aug 2026. The behaviour predates this entry; the entry records it. To be tabled at the next parity review |

| 5 | A hearing the transformation cannot read is reported, not swallowed | `setInformantRegisterHandler` wraps the whole build in `try { … } catch (err) { context.error(…) }` and returns `undefined` (`SetInformantRegister/index.js:159`). Every `TypeError` inside the port — an unguarded `defendant.offences.forEach`, a `courtCentre` that is `null`, a `DateService.parse` that cannot read an ordered date — is therefore absorbed. `InformantRegisterOrchestrator`'s `if (informantRegisters)` skips the rest of the flow and the orchestration still returns `Success: true`. The hearing produces no register for any authority, and nothing anywhere records that it was meant to | The same conditions raise `TransformationFailedException`, classified `NON_TRANSIENT`. The pipeline records the request `FAILED` with reason `TRANSFORMATION_FAILED` and dead-letters the delivery with a bounded reason. The delivery budget is not spent first: no redelivery re-reads the payload differently | **The scope is failure handling only, and the boundary matters.** Where the legacy throws, this refuses; where the legacy produces no register *without* throwing, this returns an empty list and completes (entry 4). No hearing that the legacy turns into a register is turned into anything different here — the refusals are, by construction, exactly the inputs on which the legacy emits nothing. This is the "end of swallowed errors" half of the transport-reliability change the Option 2 page sanctions, which entry 2 records for the *final POST* only; the transformation's own swallow is a second site of the same defect and is recorded separately rather than read into entry 2's wording. Constitution Principle VI: a hearing that fails must be visible and replayable, and dead-lettering is what makes the parked request recoverable through the documented `FAILED` → replay path. Pinned by the refusal assertions in `JsonTest`, `DefendantContextBuilderTest`, `VocabularyBuilderTest` and `HearingDatesTest`, each of which cites the legacy line it reproduces | **Sign-off pending** — raised by the Story-2 code review, 22 Aug 2026, which found the behaviour attributed to entry 2. To be tabled at the next parity review alongside entry 4 |
