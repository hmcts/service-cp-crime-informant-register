# Parity Deviations Register

Behaviour-parity is the rule (constitution Principle I): the observable behaviour of this
service is defined by the legacy informant register function app plus the golden fixtures.
Every deliberate divergence from legacy behaviour MUST be recorded here, with review sign-off,
before the code that introduces it merges. The golden-file harness fails on any divergence
not listed in this register.

| # | Deviation | Legacy behaviour | New behaviour | Rationale | Approved |
|---|---|---|---|---|---|
| 1 | Verified TLS on the payload fetch | Redis client connects with `rejectUnauthorized: false` (certificate checks disabled) | TLS certificate verification enabled, platform CA bundle | Security defect (D14 in the design defect register); not observable in register output | Design sign-off 19 Aug 2026 (Option 2 page: the only improvements in this delivery are transport-level); asserted by `LivePayloadConfigTest.TransportSecurity` |
| 2 | Transport reliability | Final POST errors swallowed at three levels; no retry; hearing silently lost | Failures retry (broker redelivery), then dead-letter with alerting; POST client retries connect/IO/5xx/429; a refusal is parked at once rather than retried to exhaustion; success is `202 Accepted` and any other 2xx is treated as a failure rather than as an accepted command | The single agreed improvement of the lift-and-shift (Option 2 page, "Scope"); changes failure behaviour only, never successful-path output. The 202 rule is the same principle applied to an ambiguous success: a command that was not accepted was not enqueued, and calling it success would lose the register with the log saying it was sent | Design sign-off 19 Aug 2026 |
| 3 | **Waiver — alert wiring deferred (CRA-220 only)** | No signal of any kind: no logs, no metrics, no alerts | CRA-220 ships the full failure signal — a sanitised ERROR log and a failure metric on every failure path, plus countable dead-lettered messages (spec FR-017) — but **no dashboards or alert rules**. Alert wiring lands with the later operability story (`doc/TECHNICAL_DESIGN.md`, "Later stories": DLQ alert wiring and reconciliation tooling) | Named waiver of constitution Principle VI's "alerting is required in addition" clause, scoped to this increment. The walking skeleton has no real submission adapter, so there is nothing yet whose failure an on-call alert would act on; the emitted metrics are the prerequisite the alert rules are built from, and shipping them first keeps the waiver time-boxed. Still a strict improvement on legacy silence. Dead-letter **depth** is observed in deployed environments from Azure Monitor's native Service Bus metric `DeadletteredMessages` rather than polled by service code, so the deferred DLQ alert will be wired onto that platform metric; the service's own `informantregister_deadlettered_total{reason=…}` counter ships now alongside it | Gate-2 spec review, 20 Aug 2026 — expires when the operability story lands; follow-up ticket to be raised on the CRA board |
| 4 | Legacy undated cache key read as a second lookup | `getCacheKey` builds one key from the hearing date it was given, and `getResultFromCache` performs exactly one `GET` with it | The dated key is read first; when it holds nothing the legacy undated twin is read before the query side is asked | The producer publishes the payload under both key forms (design doc §2.1; `doc/API_CONTRACTS.md`, `hearingDay` semantics; Option 2 page row 1, "both key forms"), so reading only the dated form sends every legacy-cached hearing to the query API. The cost is that an expired dated key can be answered by a still-live undated twin holding a later share of the same hearing, where legacy would have queried Results — accepted because both keys are written by the same producer in the same operation | Option 2 design page, 19 Aug 2026 (row 1); asserted by `CachedHearingPayloadAdapterTest.RegisteredDeviations` |
| 5 | A cache that cannot be reached is a miss | `getResultFromCache` catches a failed `GET` and returns `null`, but the client is obtained *outside* that catch — so a failed connection (TLS, auth, refused connect) throws out of the activity, the query side is never asked, and the orchestration reports success having produced nothing | Every failure of the cache technology, connection failures included, is reported as a miss, so the query side still gets its turn; only a fault that is not the cache's own escapes | Design rules classify "both Redis and the fallback unavailable" as the transient case, which presumes the fallback is attempted when the cache is unavailable; and legacy's own behaviour on this path is the silent success this service exists to end (deviation 2). Absorbed at the cache adapter and scoped to `RedisException`, so nothing else is swallowed | Design rules ("Processing State Machine", transient list); asserted by `LettuceHearingPayloadCacheIT.Unreachable` |
| 6 | No fragments is an empty list, not `undefined` | `SetInformantRegisterBuilder.build()` returns `undefined` twice over — for a hearing with neither `prosecutionCases` nor `courtApplications`, and for one whose loop yields no fragments. `InformantRegisterOrchestrator`'s `if (informantRegisters)` then skips subscription matching, the outbound mapping and the POST, and the orchestration still reports success | `RegisterBuilder.build()` returns an empty list. The pipeline records the run COMPLETED with the reason `no-authorities` | Nothing is submitted on either side and no register content differs: the divergence is that the port's answer is a value the state machine can record rather than an absence every caller has to test for. `design_rules.md` ("Processing State Machine") requires exactly that — a hearing that legitimately produces no authorities ends COMPLETED with `no-authorities`, a business outcome and not an error. Pinned by `RegisterBuilderParityTest.assertLegacyProducedNothing`, which asserts the empty list on cases 08 and 09 and fails on a populated one — a port that found authorities the legacy did not is an unregistered divergence and must not reach a prosecuting authority. Note the boundary: this covers a hearing the legacy has *no register for*. A hearing the legacy *throws* on is a different case and is covered by entry 7 — those now surface as a non-transient failure and dead-letter, never as an empty result | **Sign-off pending** — raised by the Story-2 code review, 22 Aug 2026. The behaviour predates this entry; the entry records it. To be tabled at the next parity review |
| 7 | A hearing the transformation cannot read is reported, not swallowed | `setInformantRegisterHandler` wraps the whole build in `try { … } catch (err) { context.error(…) }` and returns `undefined` (`SetInformantRegister/index.js:159`). Every `TypeError` inside the port — an unguarded `defendant.offences.forEach`, a `courtCentre` that is `null`, a `DateService.parse` that cannot read an ordered date — is therefore absorbed. `InformantRegisterOrchestrator`'s `if (informantRegisters)` skips the rest of the flow and the orchestration still returns `Success: true`. The hearing produces no register for any authority, and nothing anywhere records that it was meant to | The same conditions raise `TransformationFailedException`, classified `NON_TRANSIENT`. The pipeline records the request `FAILED` with reason `TRANSFORMATION_FAILED` and dead-letters the delivery with a bounded reason. The delivery budget is not spent first: no redelivery re-reads the payload differently | **The scope is failure handling only, and the boundary matters.** Where the legacy throws, this refuses; where the legacy produces no register *without* throwing, this returns an empty list and completes (entry 6). No hearing that the legacy turns into a register is turned into anything different here — the refusals are, by construction, exactly the inputs on which the legacy emits nothing. This is the "end of swallowed errors" half of the transport-reliability change the Option 2 page sanctions, which entry 2 records for the *final POST* only; the transformation's own swallow is a second site of the same defect and is recorded separately rather than read into entry 2's wording. Constitution Principle VI: a hearing that fails must be visible and replayable, and dead-lettering is what makes the parked request recoverable through the documented `FAILED` → replay path. Pinned by the refusal assertions in `JsonTest`, `DefendantContextBuilderTest`, `VocabularyBuilderTest` and `HearingDatesTest`, each of which cites the legacy line it reproduces | **Sign-off pending** — raised by the Story-2 code review, 22 Aug 2026, which found the behaviour attributed to entry 2. To be tabled at the next parity review alongside entry 6 |
| 8 | **`Retry-After` is honoured in delta-seconds only, and bounded** (sub-decision of #2) | No retry of any kind, so no `Retry-After` was read: a 429 was swallowed with everything else | A 429's `Retry-After` is acted on when it is delta-seconds, bounded above by `informantregister.results.max-backoff`. An HTTP-date, an unreadable value, or no header at all falls back to the exponential back-off, under the same ceiling | Recorded because #2 said "the delay the server asked for, capped" without saying which forms are read. Acting on an HTTP-date would subtract a remote clock's idea of now from this pod's, and a server a few minutes ahead would park a run past the claim lease it holds (`design_rules.md`, "Claim timing") — the header is therefore classified before it is read rather than parsed and caught. The ceiling exists for the same reason and applies to a server-supplied delay exactly as it does to the back-off. Asserted by `ResultsCommandGatewayTest`: an HTTP-date, an unparseable value and a value beyond the ceiling each have their own case | Raised at the story-3 code review, 22 Aug 2026; sub-decision of #2 (design sign-off 19 Aug 2026), to be confirmed with the design authority |
| 9 | **An unmapped verdict code yields a verdict with no type, not a null one** | `VerdictCodeMapping.getVerdictType` returns `null` for every code outside `G`, `N`, `PSJ` (and for the literal `None`), and `OffenceMapper.js:69-73` writes that straight into the verdict object. `JSON.stringify` keeps an explicit null, so the POSTed body carries `"verdictType": null` inside a component the frozen contract types as a `string` — a schema violation the consumer would have to reject, on a hearing that is otherwise fine | The verdict is still emitted, still carrying the `verdictCode` the payload sent and the `verdictDate` beside it; only the derived `verdictType` is absent rather than null, under `@JsonInclude(NON_NULL)` | The typed outbound tree cannot represent a null in a string component and must not try: widening it would mean relaxing somebody else's closed contract locally, which constitution Principle III forbids. Nothing about *which* verdicts reach a register changes, and nothing about the two components the payload actually supplies changes — the difference is confined to a derived value the legacy could not name either. Absent is also the shape the schema calls valid for a component it does not require. Asserted by `OffenceMapperTest.PinnedOddities.an_unmapped_verdict_code_yields_a_verdict_with_no_type`, which pins both halves: the code survives, the type is absent | **Sign-off pending** — raised by the aggregation-mapper port, 23 Aug 2026. To be tabled at the next parity review alongside entries 6 and 7 |
| 10 | **A register component that cannot be typed is parked, not POSTed** | The aggregation carries the fragment's identifiers and timestamps as whatever strings the earlier steps produced, and `axios.post` sends them. A hearing id that is not a UUID, or a register date that came out as the literal `"Invalid dateZ"` (D9 + D10, parity-pack `s05`), is therefore POSTed into a `uuid`- or `date-time`-typed component and rejected by the consumer's schema — which the legacy neither inspects nor logs, so the register is lost silently | The same values raise `TransformationFailedException`, classified `NON_TRANSIENT`. The request is recorded `FAILED` and the delivery dead-lettered with a bounded reason | The consumer's own binding types these as `UUID` and `ZonedDateTime`, so the typed tree has nowhere to put a value of another shape and inventing one would be worse than refusing. **The outcome is the same either way — no register reaches the authority** — so this changes only whether the failure is visible: it is the "end of swallowed errors" principle of entry 2 applied at the last boundary, exactly as entry 7 applies it at the first. The values themselves are never quoted into the reason, only the component's name (`research.md` §11, bounded reason codes). Note the narrowness: a *well-formed* value keeps its rendering byte for byte, D9's misleading `Z` included — a parsed timestamp re-renders as the string it was parsed from, which is what the golden-parity twins confirm. Asserted by `AggregationMapperTest.TypedBoundary` | **Sign-off pending** — raised by the aggregation-mapper port, 23 Aug 2026. Depends on the open Results-team question the parity pack records for `s05`: whether `"Invalid dateZ"` should be reproduced or refused. Refusing is recorded here so the choice is visible; the answer may retire this entry |
